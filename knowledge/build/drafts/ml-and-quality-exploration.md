# ML boundary & quality-signal exploration

> **Status: exploration notes.** Findings + directions from a design session, not
> queued work. Extends [Immich dependency decision](/build/immich-dependency-decision.md)
> and feeds [open questions](/build/open-questions.md). Promote items into
> `progress.md` when scheduled.

## Scope

What we actually depend on Immich's ML for, what it would take to own those pieces,
where CLIP/Claude fit for captioning, and whether the `quality` stage's two scores
earn their keep.

---

## Key findings

### 1. What Immich ML actually gives us
- **Face detection → stable person identity.** Downstream keys off Immich's
  `person_id`, not raw faces: `sync` stores per-photo people, `lead_faces` resolves
  leads by which *persons* Immich assigned, `select` boosts group shots + guarantees
  lead coverage.
- **Duplicate grouping** → `duplicate_group_id`, consumed by `select` to cull dupes.
- **Thumbnails** — generated by Immich's async job cascade on upload; the app only
  *fetches* (`GET /assets/{id}/thumbnail`), never generates.
- **NOT CLIP embeddings** — the REST API exposes none; the app computes its own via
  `open_clip` (ViT-L/14 + LAION head). So Immich carries no *hard* ML.

### 2. Duplicate selection is safe to drop
- Only consumer is `select`'s `duplicate_group_id` check. Removing it loses
  exact/near-dup culling but nothing else; aesthetic + near-dup-by-embedding stay.

### 3. Owning face detection ourselves
- **Detection + embedding = easy.** Same model as Immich: InsightFace `buffalo_l`
  (SCRFD + ArcFace 512-d).
- **Identity/clustering = the hard part** Immich does for free (stable person IDs).
- **Effort depends on scope:**
  - *Lead-only* ("does this photo contain a lead?") → **trivial**: embed reference
    lead faces, cosine-match against album faces. No clustering.
  - *+ group-shot / recognized-person boost* → needs album-scoped embedding
    clustering (DBSCAN/agglomerative). Only real work.

### 4. immich-ml can run standalone (skip the server)
- `immich-machine-learning` is a stateless FastAPI service (`POST /predict`) — no
  server/Postgres/Redis needed. Returns face boxes + ArcFace + CLIP embeddings.
- **You inherit** person clustering, dup grouping, the job queue, and thumbnails —
  all of which live in immich-server, not the ML container.

### 5. Aesthetic score via Immich ML — no (score itself), maybe (CLIP half)
- Immich ML has **no aesthetic model** (only CLIP + facial-recognition tasks), so the
  *score* is never available directly — only the CLIP *half* could be offloaded (run
  the tiny LAION head locally on Immich's embedding).
- **Model swap is feasible and the right model exists** (researched 2026-07-22):
  - Immich's CLIP model is admin-configurable (Settings → ML → Smart Search → CLIP
    model, paste the name from the immich-app HF collection).
  - `immich-app/ViT-L-14__openai` is an **OpenCLIP ONNX export of OpenAI ViT-L/14**,
    768-d — same architecture/weights/family the LAION head expects (default is
    `ViT-B-32`, 512-d, so a swap is required).
- **Residual risks (unconfirmed, would need an empirical check):**
  - **QuickGELU.** App uses `ViT-L-14-quickgelu` on purpose (plain `ViT-L-14` gives
    "subtly wrong features"). Immich's export is named `ViT-L-14__openai` — **no
    `quickgelu` suffix**, though Immich uses that suffix elsewhere (e.g.
    `ViT-H-14-378-quickgelu__dfn5b`). Yellow flag it may be the plain variant; not
    confirmed either way.
  - **Preprocessing parity** (Immich ONNX resize/crop/normalize vs open_clip) →
    possible small score drift.
  - **Settle it by**: embed same images via both, compare cosine (want ≈0.999) + LAION
    scores. Local proxy: compare open_clip plain vs quickgelu embeddings.
- **Operational / strategic cost:** changing the model **re-embeds all Immich assets**
  and is Immich's *global* search model (can't scope to just the pipeline); re-introduces
  the ML container + per-image round-trip. **Opposite** of the simplify-the-stack
  direction — only worth it if keeping Immich anyway AND wanting open_clip out of the
  app process. Otherwise keep aesthetics in-process.

### 6. Captioning: CLIP can't, Claude does
- CLIP is a *matching/embedding* model (contrastive) — it scores image↔text, has no
  text decoder, **cannot generate** captions (only retrieval from a fixed list).
- The `caption` stage correctly uses **Claude** (generative VLM). Local CLIP does the
  *judging* jobs (aesthetics, near-dup similarity); Claude does the *authoring*.

### 7. Stage/segment-level captions via Claude — easy
- Claude accepts **multiple images per request**; the captioner prompt is already a
  list `[context, image]` → make it `[context, image, image, …]`.
- Core change is the **system prompt** ("these are one scene; write one caption").
- Decisions: which/how-many photos (cap ~4–8 by score, capture-order), segment-level
  grounding, store on a new `Segment.caption` column (own path, not `PhotoAnalyzer`).
- Bonus: **fewer** API calls (one per segment) and better captions (whole-scene view).

### 8. Blur vs aesthetic — blur is unused but NOT redundant
- `blur_score` is **write-only**: computed + stored by `quality`, read by **nothing**
  downstream. `aesthetic_score` is `select`'s primary ranking key.
- Measured on **118 real photos** (app DB): Pearson **0.307**, Spearman **0.331**,
  **R² 0.094** → blur explains ~9% of aesthetic variance.
- A genuinely blurry photo had an **above-mean aesthetic score** → soft shots can win
  a scene on aesthetics alone. **Blur carries signal the aesthetic model misses.**

### 9. Blur scale
- Raw `cv2.Laplacian(gray_thumbnail).var()` — **no normalization**, unbounded `[0,∞)`.
  Observed ~484–5251 (mean 2235, sd 1033) on one album.
- **Content-dependent, not absolute**: a focused plain wall scores low, a busy scene
  high. A global 0–10 map implies cross-scene comparability the metric lacks.
- If normalizing: prefer a **raw-unit cull floor** or **within-scene / percentile**
  normalization over a fixed absolute 0–10.

## Improvement areas to explore

Roughly ordered by payoff-to-effort:

1. **Wire `blur_score` into `select`** — a raw-unit cull floor (threshold from the
   album's own distribution) or a within-scene penalty. Cheap; makes an already-computed
   signal earn its keep. *Con:* content-dependence means a global threshold is imperfect.
2. **Stage/segment-level captions** via Claude multi-image + `Segment.caption`.
   Pro: fewer calls, richer captions. *Con:* new stage + storage + grounding.
3. **Drop duplicate selection** — small, unblocks skipping Immich's dedup role.
4. **Lead-only face matching in-process** (InsightFace `buffalo_l`) — avoids clustering
   entirely if group-boost is sacrificed. Pro: removes the hardest Immich dependency.
   *Con:* loses "recognized person" group boost unless clustering added.
5. **Decide the Immich boundary** — standalone `immich-ml` vs fully in-process. If
   dropping the server, also **own thumbnail generation** (few lines of OpenCV/Pillow).
6. **Zero-shot CLIP scene classification** (landscape/city, group/single) as an extra
   `select` signal — keep the CLIP text tower (currently dropped to save ~0.5 GB).
   Pro: no training, reuses loaded model. *Con:* fuzzy categories; a trained head is
   better if accuracy matters.

## What to keep as-is
- **Aesthetic scoring in-process** (open_clip + LAION head) — self-contained, and the
  hard ML Immich does *not* carry. Don't route it through Immich ML.
- **Claude for captions** — right tool; CLIP can't generate.
