Architecture note · photobook-transformer

The transform pipeline runs as a DAG, not a line.

Ten @task stages turn Immich assets into a photo book. flow/_flow.py runs them as a DAG: a sequential spine of four stages sharing one DB session, plus two concurrent fan-out groups that each open their own pooled session per worker thread. Here's the shape, and the mechanism that makes it safe.

Then vs now

Build step 25 turned the dependency shape into the execution shape.

Original design (steps 1–24)

Linear chain

One shared Session, committed after every stage. Simple, resumable, one DB connection — each stage isolated its own per-photo failures, so no Prefect-level fan-out was needed to get correct. Left real concurrency on the table: the data dependencies were a DAG the whole time.

Current (step 25, merged)

Diamond DAG

Three stages need only sync; two branches feed assemble. Each fan-out stage now opens its own pooled session per worker thread and .submit()s to Prefect's ThreadPoolTaskRunner, so the two independent groups actually run concurrently.

Where the parallelism is

Two fan-out groups, each writing disjoint state.

GroupStagesWhy independentJoins at
after sync resolve-leads · quality · cluster Each reads only Photo rows and writes disjoint columns — Person.is_lead, blur/aesthetic/embedding, and segment/scene. None reads another's output. select
after select enhance→render · caption Both consume the selected=True set; render makes JPEGs, caption makes text. enhance→render is itself a hard chain (render needs enhance's XMP sidecars). assemble

In group 1 the floor is quality (per-photo ML scoring). In group 2 it's the enhance→render chain — render shells out to darktable-cli — so caption runs in its shadow for free wall-clock time.

How it's implemented

One structural idea — own session per concurrent task — plus a few submit() / result() calls.

1 · Session ownership. A shared SQLAlchemy Session isn't thread-safe, so a stage takes a factory (never a live session) and opens the session inside run, on whichever thread runs it — which is what makes the same instance safe to .submit().

SessionFactory = Callable[[], AbstractContextManager[Session]]

# sequential — reuses the flow's shared session (a reuse() singleton that yields
# it without closing) and runs inline; run() commits the shared session
SyncStage(client, album_id, reuse(db_session)).run_as_task()

# fan-out — its OWN pooled connection per worker thread; run() opens it, commits,
# and closes it. No builder needed: the unit holds only the factory.
QualityStage(client, aesthetic, album_id, session_factory, embedder=e).to_task().submit()

2 · The flow body. .submit() schedules on Prefect 3's ThreadPoolTaskRunner; .result() blocks and re-raises. Joining enhance's future before render/caption are submitted keeps them strictly after enhance's commit.

shared = reuse(db_session)          # sequential stages reuse this; run() commits, never closes

SyncStage(client, album_id, shared).run_as_task()   # inline; run() commits the shared session

# ── group 1: independent after sync ──
g1 = [
    LeadFaceResolver(client, album_id, config, album_dir, session_factory).to_task().submit(),
    QualityStage(client, aesthetic, album_id, session_factory, embedder=e).to_task().submit(),
    ClusterStage(album_id, session_factory).to_task().submit(),
]
for f in g1:
    f.result()                      # join: blocks + re-raises any stage error

db_session.expire_all()             # drop stale identity-map state
SelectStage(similarity, album_id, shared).run_as_task()

# ── group 2: enhance first, then render‖caption ──
EnhanceStage(analyzer, client, album_id, session_factory).to_task().submit().result()
render_f  = RenderStage(client, renderer, album_id, session_factory).to_task().submit()
caption_f = CaptionStage(analyzer, album_id, session_factory).to_task().submit()
for f in (render_f, caption_f):
    f.result()

AssembleStage(albums_dir, album_id, shared).run_as_task()
FulfillStage(printer, album_id, shared).run_as_task()

What it costs

The real edges the current design has to mind.

ConcernDetail
connection poolConcurrency peaks at 3. Default QueuePool is 5 + 10 overflow = 15, so no change needed now. Size pool_size only if a stage's internal per-photo loop later becomes fan-out.
failure isolationEach task's own with session_factory() rolls back independently — one group-1 failure no longer poisons a shared transaction, and .result() still aborts the run before select.
read-after-writeCommit the shared session before each fan-out so threads read committed rows; expire_all() after the join so select/assemble re-read what the workers wrote.
testsThe SQLite test session can't cross threads. Unit tests inject a session_factory handing out independent doubles (or run the runner serially); real concurrency stays on the pgvector TestContainers suite.
Net The whole mechanism is own session per concurrent task + two submit/result fences. The real win lands in group 2, where caption disappears entirely into the shadow of the enhance→render chain.
